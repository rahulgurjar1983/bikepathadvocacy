# Spec 16: A community proposal people can judge

## 1. Purpose

Lead with what the proposed package would deliver, what it would change for the community, its cost and the next decision. Then show how the routes and local works deliver that outcome. Councillors need a choice they can explain and progress. Residents need to understand their trips and their street.

The owner's examples of 40 schools, 500 parking spaces and 20 roads describe the desired form of the report. They are not measured results, targets, constraints or defaults. Never copy them into a real report or tune inputs to reach them.

The report can show a useful network concept with stated design assumptions while its evidence-backed shortlist is small or empty. Keep those packages distinct. Missing field checks must lead to a focused next step.

The report order is proposal and trade-offs, network map, options, neighbourhood impacts, street plans, delivery, then evidence. It remains one offline HTML file. Unknown evidence is a useful result; it must not become zero impact or a claimed benefit.

This spec amends `FR-9.3`, `FR-9.4`, `FR-13.5`, `FR-13.6`, `FR-13.15` and `FR-15.2`, `FR-15.3`, `FR-15.14`, `FR-15.19`. Keep the other rules for safety, private files, sources and figures. A headline may need more proof than the model score. Keep that score with its label and explain the gap between the two.

## 3. Shared data rules

The extra source file is optional. Old commands must still work. A missing part gets a reason and a status. The tool can know parking loss before it can count school links or price the works. Show each of those states as it is. Later rows fill the gaps from sources.

Give each school site, gate, home node, road work, crossing, option and stage a stable ID. Use those IDs to join records and avoid counting the same thing twice. Sort saved records so a fresh run gives the same bytes. Save the files needed to check each displayed number. Public home data stays grouped; it must not show who lives at an address.

A zero means the tool checked the full set and found none. A missing source, unbuilt check or unknown site means it cannot yet give an answer. Say which it is. A total from only part of the data must say what is left out. Correct sums do not prove that the source describes the street today.

Show the kinds of route the plan would build. A path along a verge may be shared with people walking. A calm street may still have a hard crossing. A line on the map or a good score does not prove child safety or that more people will ride.

## 5. Loop work

For a row that cites `FR-16`, read its rule and cases here, plus the scope and shared data rules. Read the parts of spec 15 and older specs that the row names. Build each row with small tests that fail first, then code, fresh outputs and green CI. Parts owned by later rows may say not yet built.

`Q1.6` owns the shared record. `Q1.7` owns the opening and page order. The `C1` rows add route, school, people, road and local proof, then choices and delivery. `Q2.4` comes before local area views and options to load their sources, costs and the next ask. `C1.0` adds conditional concepts once route, school, people, works and metadata contracts exist. `C1.12` owns the focused survey plan. `Q1.8` and `Q1.9` still run before `C1.10`, which proves the real report as a whole. Snapshot upgrades and cache work follow the community build; no existing check is waived.

A mock test cannot prove a real route, field check, grant or school gate. If a source is missing, build the way to read and check it, and show an honest unknown result. Keep the separate evidence task open. Do not wait for a person when the code and truthful report can be built without them.

Keep Sonnet/Sol and the effort rule of `FR-0.32`. This work does not enable larger models, paid fallbacks or more agents.
